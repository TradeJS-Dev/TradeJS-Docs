MCP даёт агенту доступ к данным работающего TradeJS. Через него можно посмотреть
свечи, сохранённые сигналы и результаты бэктестов. С отдельным разрешением агент
может запустить бэктест на сервере.

MCP доступен по адресу `https://YOUR_APP_HOST/mcp`, где `YOUR_APP_HOST` нужно
заменить на адрес вашего приложения. Посмотреть адрес и список подключений
можно в разделе **MCP** в боковом меню TradeJS.

В локальной стабильной версии `3.1.28` MCP пока отсутствует. Для подключения
нужны работающий сервер TradeJS с MCP и учётная запись на этом сервере.

## Подключение Codex

Выполните в терминале, подставив адрес приложения:

```bash
codex mcp add tradejs --url https://YOUR_APP_HOST/mcp
codex mcp login tradejs --scopes market:read,runtime:read,backtests:read
```

В браузере войдите в TradeJS и разрешите чтение данных. Чтобы агент мог
запускать бэктесты, добавьте `backtests:run` в `--scopes` при входе и подтвердите
это право на странице подключения.

Codex CLI и приложение Codex могут использовать одно подключение.
Если инструменты TradeJS не появились, обновите подключение или перезапустите
клиент. Отдельный API-ключ не нужен.

## Подключение Claude Code

Выполните в терминале:

```bash
claude mcp add --transport http tradejs https://YOUR_APP_HOST/mcp
```

В Claude Code откройте [`/mcp`](https://code.claude.com/docs/en/mcp), выберите TradeJS и пройдите авторизацию
в браузере. Проверьте имя клиента, адрес возврата и запрашиваемые права перед
подтверждением. Вход и выдачу прав нужно выполнить самостоятельно.

## Первый запрос

Начните с запроса **«Проверь подключение к TradeJS и скажи, какие данные тебе доступны»**.
Агент может проверить подключение через `tradejs_info`.

| Задача | Что попросить у агента |
| --- | --- |
| Посмотреть свечи | Покажи последние 15-минутные свечи BTCUSDT на Binance. |
| Разобрать сигналы | Покажи сохранённые сигналы TrendShift на BTCUSDT за последние сутки в `production`. |
| Прочитать отчёт | Найди последний бэктест HeadAndShoulders. Покажи число закрытых сделок, итог после издержек и просадку. |
| Запустить бэктест | Найди мои сохранённые настройки HeadAndShoulders. Запусти с ними бэктест BTCUSDT на Binance за последние семь дней по сохранённым 15-минутным свечам. Покажи имя настроек и номер задачи. |

Для первых трёх запросов достаточно чтения. Для запуска нужны право
`backtests:run`, сохранённые настройки и запущенный обработчик задач на сервере.

## Данные работающего приложения

Для вопросов о работе приложения агенту также нужен `runtime_get_status`.

Кнопка **Copy context for AI** на дашборде копирует источник рыночных данных,
набор инструментов, выбранную монету, интервал, бэктест и ссылку на страницу.
Вставьте скопированный текст в чат и добавьте вопрос. Видимая область графика
не копируется. Сохранённые фигуры стратегии ассистент может получить через
`runtime_get_signal` по данным из списка сигналов.

При чтении данных работающего приложения указывайте развёртывание и период.
Инструменты принимают окно `[startTime,endTime)`: начало входит в период,
конец не входит. Один запрос к спискам может охватывать не более семи дней.
Пустая страница не завершает чтение: нужно продолжать до курсора `0`.
Курсоры списков runtime действуют 24 часа и доступны разным процессам сервера
при том же окне и фильтрах. После ошибки передачи повторите идентичный запрос.
При `CURSOR_EXPIRED` начните то же окно с курсора `0` и удаляйте повторы
по идентификаторам записей. Порядок хранения не хронологический, поэтому перенос
начала окна на время последней записи может пропустить данные.

Отсутствие сохранённых записей само по себе не означает, что стратегия
не работала. Счётчики пропуска помогают при диагностике, но для проверки
исполнения нужны отчёты с зафиксированными версиями пакетов и конфигурацией.

### Проверка развёрнутой версии

С правом `runtime:read` инструмент `runtime_get_verification` принимает
`deploymentId` и читает опубликованный владельцем приложения отчёт с проверенным
хешем. Отчёт связывает ревизию Project, фактический digest образа, состав пакетов,
счёт и состав развёртывания с наблюдением здоровья и результатом
`runtime-control verify`. Проверьте `fresh`, `report.ok` и `collection`, если
оно есть. `deploymentVerifiedAt` хранит время исходной проверки при выкладке;
позднее наблюдение его не заменяет. При отсутствии или устаревании отчёта
проверка остаётся неполной. Один heartbeat не подтверждает развёрнутую версию
или успешную проверку.

## Права доступа

| Право | Что доступно ассистенту |
| --- | --- |
| `market:read` | Торговые инструменты, текущие цены, закрытые свечи, индикаторы и покрытие данных |
| `market:backfill` | Ставить загрузку пропусков в очередь и читать покрытие от имени владельца проекта |
| `research:read` | Читать сохранённые исследования от имени владельца проекта |
| `runtime:read` | Развёртывания, настройки стратегий, сохранённые сигналы, решения, ордера и счётчики пропуска |
| `backtests:read` | Конфигурации и результаты бэктестов, состояния задач |
| `backtests:run` | Запуск и отмена бэктестов, созданных этим клиентом |
| `diagnostics:read` | Проверенные отчёты, их файлы и состояния задач |
| `diagnostics:run` | Сбор данных о работе приложения, повторное воспроизведение и проверка совпадения результатов, отмена задач этого клиента |

Ассистент видит только инструменты, разрешённые при подключении. Для чтения
развёртывания торговый счёт должен принадлежать авторизованному пользователю.
Через MCP нельзя размещать, отменять или закрывать реальные ордера, менять
конфигурацию стратегий, выполнять деплой или отправлять уведомления.

Отозвать доступ можно в разделе **MCP**. После отзыва токены перестанут
работать при следующих запросах. Токен доступа действует 15 минут,
а разрешение на подключение действует до 30 дней. При обновлении токена
клиент получает новый refresh token.

## Покрытие данных {#data-coverage}

Владелец проекта может найти набор и ряд через `coverage_list_datasets`,
а затем проверить до семи дней по UTC через `coverage_inspect`. Ответ
описывает данные на подключённом сервере TradeJS.

С правом `market:backfill` инструмент `coverage_backfill_start` по вашей
явной просьбе ставит в очередь загрузку одного набора, ряда и дня по UTC.
Это та же [очередь, что и в приложении](../getting-started/data-sync).
Инструмент `coverage_backfill_get` показывает состояние задания и оставшиеся
пропуски. На странице согласия право загрузки по умолчанию не выбрано.

## Сохранённые исследования {#saved-research}

С правом `research:read` владелец проекта может получить список сохранённых
исследований через `research_list_studies` и открыть одно через
`research_get_study`. В исследовании могут быть решение, метрики и
ограничения. Чтобы дочитать сокращённый раздел, передайте его точный
заголовок и смещение из ответа.

## Бэктесты и диагностика

`backtest_start` запускает бэктест по снимку сохранённой именованной
конфигурации из Redis. Доступны только кешированные исторические данные,
без платных запросов к ИИ, в одном процессе. Один запуск ограничен 90 прошедшими днями,
20 монетами и восемью комбинациями параметров. Краткие результаты сохраняются
и в режиме `fast`.

Перед новой диагностикой проверьте готовые отчёты через
`diagnostics_list_reports`. Если подходящего отчёта нет, `diagnostics_start`
может собрать данные о работе приложения за период до семи дней или повторно
воспроизвести работу по проверенному набору данных того же развёртывания.

Запуск возвращает `jobId`, идентификатор задачи. По нему можно узнать состояние
через `job_get`, прочитать журнал через `job_get_logs` или отменить задачу
через `job_cancel`. Отключение клиента не отменяет задачу. При повторе
идентичного запроса используйте прежний `idempotencyKey`, чтобы не создать
дубликат.

На пользователя разрешены одна активная задача и десять запусков в час.
Время выполнения ограничено часом, состояние хранится семь дней.
После перезапуска worker прерванные задачи получают статус `failed`
и автоматически не повторяются.

### Готовность воспроизведения

До запроса воспроизведения проверьте `tradejs_info.worker`. `replayAvailable`
означает наличие совместимого исполнителя на сервере. Отдельное поле
`replayReadiness` принимает `ready`, `waiting_resources` или `unknown`.
Если доступно, `replayResources` содержит время наблюдения, свободную память,
необходимый минимум и дефицит в КиБ. Это наблюдение не резервирует память:
сервер повторно проверяет её под общей блокировкой очереди. Ожидание ресурсов
не означает завершённое воспроизведение; сохраняйте идентификатор задачи,
не создавайте дубликаты. Отсутствие полей ресурсов оставляет ёмкость неизвестной.

### Журнал задачи

Вызовите `job_get_logs` с `jobId` и `offset: 0`. Параметр `limit` задаёт число
записей от 1 до 100, по умолчанию 50. Для следующей страницы передайте
`nextOffset`; значение `null` означает конец журнала.

Журнал содержит stdout и stderr со скрытыми секретами, в том числе после
ошибки задачи. Сохраняются последние 150 записей длиной до 1 000 символов.
Пока задача работает, смещения могут меняться. Поле `retainedLines` показывает
число сохранённых записей.

Если запрос вернул сохранённый результат, журнал относится к исходному
запуску. Он доступен, пока хранится на сервере.

### Файлы отчёта

`diagnostics_get_report` возвращает отчёт или его краткое содержание.
Для загрузки файлов используйте `artifact_get`. Он возвращает части в base64
размером до 48 000 байт. Продолжайте с `nextOffset` до значения `null`,
декодируйте части и соедините байты. Перед анализом проверьте общий размер
и SHA-256 из ответа, а также период и версии пакетов в отчёте.

В каталоге доступны завершённые отчёты `runtime-evidence` и `runtime-feedback-replay`,
прошедшие проверку владельца, доступа, размера и хеша. Размер каждого файла
данных или журнала ограничен 64 МиБ. Для более крупных файлов используйте
локальные команды TradeJS. Каталог принимает фильтры `deploymentId`, `kind`,
`startTime` и `endTime`, а также `offset` и `limit` (1–100, по умолчанию 20).
Передавайте `nextOffset` до значения `null`. `scanTruncated` означает, что
сам поиск на сервере неполон; исключённые наборы и сроки хранения также
ограничивают полноту.

`diagnostics_get_report.files` перечисляет доступные файлы с отдельными
размерами и SHA-256. В `artifact_get.file` можно указать `payload` по умолчанию,
`manifest.json`, `.complete` или доступный `replay.log`. Журнал, требующий скрытия
секретов, этим способом недоступен; используйте `job_get_logs`. Для большого
отчёта возвращается краткое содержание, поэтому полный текст нужно загрузить
через `payload`.

## Если подключение не работает

| Проблема | Что проверить |
| --- | --- |
| Ответ `401` | Разрешение могло истечь или быть отозвано. Пройдите авторизацию заново самостоятельно. |
| Ответ `403` для браузерного origin | Сравните адрес запроса с публичным адресом в настройках сервера. |
| Нет нужного инструмента | Проверьте выданные права в разделе **MCP**. |
| Не запускается задача | Проверьте доступность фоновых задач через `tradejs_info`. Если они недоступны, обратитесь к владельцу приложения. |

[Готовые запросы к агенту](./develop-with-an-agent) помогут проверить подключение на конкретной задаче.
